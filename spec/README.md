# 文書作成規格 第3版・文書レビュー規格 第9版(人間向け)

作成日:2026-11-11。この文書はAIに渡さなくてよい。

## 構成

```text
START.md                  AIが最初に読む入口(依頼の種類と、読むファイルの表)
common.md                 全担当が読む(記法、用語、負担の原因、author-style の読み方)
handoff.md                受け渡しに関わる担当が読む(author-style の枠、規格の間で渡す書式、記録の置き場所)
author-style-template.md  author-style のテンプレート(事項ごとの問いつき)
writing/                  文書作成規格(core、工程0〜4、文体と書き方の型、rationale)
review/                   文書レビュー規格(core、役割ファイル6つ、rationale)
agents/                   サブエージェントの定義(モデルと effort を含む)
MANUAL.md                 利用者向けマニュアル(章立てだけ。本文は未執筆)
```

author-style.md は、この規格群に含まれない。書き手が持ち、文書や状況ごとに用意する。作り方は2通りある。テンプレートに自分で記入して渡すか、AIにテンプレートの問いを尋ねてもらって答えるかである。「未記入」の欄が残っていれば、AIはその欄だけを尋ねる(handoff.md の N4)。

## 置き方

1. このフォルダを、作業フォルダの中に置く(例:`spec/`)。
2. `agents/` の7ファイルを、`.claude/agents/` に写す。
3. author-style.md を、作業フォルダに置く(まだなければ、AIが尋ねて作る)。
4. 記録は、AIが作業フォルダの `records/` に作る。消さずに残す。

```text
records/
  brief.md        依頼内容ファイル(要件定義書)
  mapping.md      対応づけ(author-style とレビュー規格の結び付け)
  boundaries.md   境界の一覧
  items.md        項目一覧(全回の指摘。AIが書く)
  decisions.md    採否表(あなたが採否を書く)
  evidence.md     根拠表(確かめた根拠の記録)
  round-1/ …      回ごとのレポートと作業ファイル
```

## 始め方

主の会話に `START.md` を読ませ、したいことを伝える。AIが、種類に応じて読むファイルを決める。

| したいこと | 伝えること |
| --- | --- |
| 相談から文書を作る(壁打ち) | 作りたい文書のイメージ。決まっていなくてよい |
| 内容が決まっている文書を書く | 書きたい文書、読者、目的。author-style.md があればその場所 |
| レビューする | 対象の文書、author-style.md の場所。2回目以降は「2回目」であること(records/ があればAIがたどる)。媒体(表示・配置)も確かめたい回は、そう伝える |
| レビューを受けて書き直す | 採否を書き入れたこと(records/decisions.md)、対象の本文 |
| 書き直しを確かめる | 「再検証」であること、変更前と変更後の本文(変更記録は records/ にある) |

rationale.md はAIに渡さない。

## 1周の流れ

1. (任意)壁打ちで、何を書くかを広げる。壁打ちメモができる。
2. 文書作成の工程1〜3で本文を書く(既にある原稿なら、ここは飛ばす)。
3. レビューの回を行う。レポート、項目一覧、採否表の3つが返る。レポートには、その回に新しく生まれた項目と、状態が変わった項目だけが載る。
4. 採否表(records/decisions.md)に採否を書く。先頭の「一括指定」に「段階3以上とフラグ付きは採用」のように書けば、該当する行は個別に書かなくてよい。個別に書いた行は、一括指定より優先される。レポートの「author-style への追記案」を見て、author-style.md を自分で更新する。
5. 書き直しを頼む。本文と変更記録が返る。構成を変える修正(規模が大)があるときは、先に草案の承認を求められる。
6. 再検証を頼む。レポートと、更新された項目一覧が返る。
7. 未解消と新規について、4〜6を繰り返すかを決める。

## モデルと effort

| 担当 | 定義ファイル | モデル | effort |
| --- | --- | --- | --- |
| Lead・窓口(主の会話) | なし | 最上位(fable)か opus | medium |
| 照合担当 | review-collator | haiku | 既定 |
| 構造担当 | review-structure | opus | high |
| 章担当 | review-chapter | opus | medium |
| 検証担当 | review-checker | opus | medium |
| 確認者 | review-verifier | opus | medium |
| 執筆 | writing-writer | opus | high |
| 改稿 | writing-reviser | opus | high |

- 要約テスト(レビュー規格 L3.11)は、定義ファイルを持たない。Leadが、最小のモデル(haiku)を指定して起動する。
- 検索の道具(WebSearch、WebFetch)を持つのは、検証担当だけである。ほかの担当は、確かめたい事柄を「検証の要求」として返し、Lead・窓口が検証担当に回す。
- 章担当は人数が最も多く、使用量を支配する。設定を見直すときは、review/rationale.md の実験の手順で比べる。
- 結果が足りないときは、モデルを替える前に effort を一段上げる。
- 環境変数 `CLAUDE_CODE_EFFORT_LEVEL` を設定していると、定義ファイルの effort より優先される。
